# GrokFree 迭代方案 —— 参考 grok-app 的融合与借鉴

> 写作时间：2026-08。对照对象：[RongleCat/grok-app](https://github.com/RongleCat/grok-app)（MIT，非官方 Tauri 2 桌面工作台，对照版本 v0.2.26 @ `fcfa63d`）。
> 本文基于**通读两边源码**得出，GrokFree 侧给出具体文件与行为指针；未在 Windows 真机复现卡死，涉及推断处均已标注置信度。

## TL;DR

1. **切项目卡死（P0）最可能的原因是前端一个全局 `busy` 标志把「任意会话的整轮对话」和「切换/恢复操作」串联在了一起**：只要有一轮对话在跑（可能持续几分钟），点其他项目的会话恢复就会被直接拒绝、按钮禁用，看起来就是"卡死"。其次是恢复链路不可取消 + 超时长达 600 秒。详见 [§2](#2-p0切换项目为什么会卡)。
2. grok-app 值得抄的不是功能，而是**进程与轮次治理策略**：切换会话永不取消/阻塞在忙的轮次上、进程上限 + 闲置回收、流静默看门狗（只提示不自动取消）、崩溃后轮次修复、权限分级持久化。
3. grok-app 的 IM 桥接、手机镜像、桌宠/皮肤、语音、图像生成等**不建议搬**——那是另一个产品的野心，单人 Windows 自用维护不动（grok-app 源码约 65 万行，GrokFree 约 1.4 万行）。
4. 计划分三阶段：**先解卡（改动集中在 6 个文件内）→ 借鉴进程/权限治理 → 可选增强**。

## 1. 两个项目各是什么

| 维度 | GrokFree（本仓库） | grok-app（参考仓库） |
|------|-------------------|---------------------|
| 定位 | 个人自用的 Windows 桌面客户端 | 面向大众发布的跨平台桌面工作台 |
| 技术栈 | Tauri 2 + React + TS + Rust；zustand；无组件库 | Tauri 2 + React + TS + Rust；shadcn/CodeMirror；pnpm workspace |
| 规模 | 前端 + Rust 合计约 1.4 万行 | 前端约 50 万行、Rust 约 14.5 万行（含测试） |
| 驱动 CLI 方式 | ACP over stdio，`grok agent`（`src-tauri/src/acp/client.rs`） | 同为 ACP over stdio `grok agent stdio`（`src-tauri/src/acp_client.rs`），另有 mock 模式 |
| 进程模型 | **一个活跃会话一个进程**（`Supervisor`），手动"休眠"即杀进程 | **一个会话一个进程 + 池化治理**：live / background-busy / parked-ready 三态，上限默认 8（可到 32），闲置 30 分钟自动回收（`session_manager/`、`process_limits.rs`） |
| 项目/会话模型 | 项目 = 一个 cwd；会话 meta 存 `%LOCALAPPDATA%\GrokFree\desktop-state.json`；历史**直接回放 CLI 的 `~/.grok/sessions/**/chat_history.jsonl`** | 独立存储 `~/.grok-app`（projects / sessions index / 每会话 messages 日志），CLI 历史可"导入"；写盘有节流（`store.rs`、`journal_throttle.rs`） |
| 切换会话时对忙轮次的处理 | 前端全局 `busy` 期间**拒绝恢复其他会话**（见 §2） | 明确策略：**切换永不取消忙轮次**，降级为 background 继续泵事件；进程不跨会话抢占（`session_manager/mod.rs` 头注释 I01–I03） |
| 权限 | ask / auto / always-approve 三档全局设置；弹窗允许一次 | Ask / AllowOnce / AllowForSession / AcceptEdits / DontAsk / YOLO 分级 + 会话级允许缓存 + 写回 CLI `config.toml [permission]` 规则（`permission.rs`、`permission_rules.rs`） |
| 健壮性机制 | 请求 600s 超时；进程退出侦测（300ms 轮询 + client_gen 防陈旧事件）；Job Object 兜底杀进程 | 流静默看门狗（默认 600s，只弹"继续等/结束"，**从不自动取消**）、长工具心跳 25s、崩溃遗留轮次修复（turn lease）、软重启（`stream_stall.rs`、`tool_heartbeat.rs`、`turn_lease.rs`、`turn_interrupt.rs`） |

两边的底层协议和进程形态其实**同构**（都是 ACP + 每会话一个 CLI 进程），所以 grok-app 的治理策略可以按机制逐条移植，不需要重写。

## 2. P0：切换项目为什么会卡

### 2.1 「切项目」在代码里实际发生什么

点侧栏项目本身很便宜（`src/App.tsx` 的 `onSelectProject`：换 `activeProjectId`、清空跨项目的 `activeSessionId`，外加一次异步 git 探测，git 探测已在 `spawn_blocking` 里，不会卡 UI）。**真正重的是紧接着的动作**：点该项目下的休眠会话 → `resumeMeta`（`src/hooks/useResumeSession.ts`）→ Rust `Supervisor::resume_session`（`src-tauri/src/supervisor/mod.rs`）。

### 2.2 嫌疑排名（按可能性）

**嫌疑 ①（最可能）：全局 `busy` 把所有导航都锁死了。**

- `sendPrompt` 在**整轮对话期间**持有全局 `busy=true`（`src/hooks/useComposerActions.ts` 第 42–56 行）。一轮带工具调用的对话跑几分钟很正常。
- 而 `resumeMeta` / `resumeDiskSession` 开头就有 `if (opts.busy || inFlight.current)` 直接拒绝并 flash「正在恢复会话，请稍候…」（`useResumeSession.ts` 第 64、116 行）；侧栏/顶栏多个按钮也吃同一个 `busy` 被禁用。
- 结果：**只要任何项目里有一轮对话在跑，切到别的项目点会话就没有反应**（或只闪一条 toast）。用户感知就是"切项目卡死"。这不是死锁，是设计把不相干的操作串行化了。

**嫌疑 ②：恢复链路不可取消，超时上限过长。**

真正恢复时的串行链路（全部 `await`，期间 `busy=true`、无取消按钮）：

1. `hibernate` 杀旧进程并等待退出（`supervisor/mod.rs` 第 704 行起）；
2. `probe_environment`：每次 spawn 都跑 `grok --version` + `where grok`（`src-tauri/src/config.rs` `run_version`/`which_on_path`），**没有超时**——Node 系 CLI 冷启动 1–3 秒起步，遇到杀毒软件扫描或 PATH 上有网络盘可以无限挂起；
3. spawn `grok agent` → `initialize` → `session/load`，每个请求超时是 **600 秒**（`src-tauri/src/acp/client.rs` 第 323 行）。`session/load` 要 CLI 回放整个历史，大会话本身就慢；CLI 若挂住，就是最长 10 分钟的白等。

叠加嫌疑 ①：恢复挂住期间 `busy` 一直为真，其他一切会话操作都被拒。**"有时卡、有时不卡"与"大会话/CLI 状态不好时更容易卡"都能被这两条解释。**

**嫌疑 ③（能造成真·窗口冻结，概率较低但值得排除）：同步 Tauri command 在主线程上抢锁。**

Tauri 2 里**非 async 的 command 在主线程执行**。GrokFree 有一批同步 command（`get_app_state`、`rename_session`、`remove_session_meta`、`update_prefs` 等，见 `src-tauri/src/commands/mod.rs` / `commands/disk.rs`）都要拿 `desktop` 这把 `parking_lot::Mutex`；而后台任务（create/resume/hibernate）会**持锁执行 `st.save()` 写盘**（`supervisor/mod.rs` 多处）。若写盘被 Defender 之类拖慢，主线程在锁上等待 → **整个窗口白屏/无响应**。这是唯一能解释"Windows 报『未响应』"级别冻结的机制。

**嫌疑 ④（次要）：超大 transcript 的主线程渲染抖动。** 历史回放有 50 条首屏 + 展开上限 500 的保护（`useSessionActions.ts`），流式更新也做了引用比较去抖（`useAgentEvents.ts`），问题不大，但没有虚拟列表，几千块的会话仍会抖。

### 2.3 怎么确认（无法复现时的排查法）

1. **先分辨冻结类型**：卡住时拖动窗口、hover 按钮——
   - 界面还会重绘、点击只弹「正在恢复会话，请稍候…」→ 嫌疑 ①/②；
   - 窗口彻底不重绘、Windows 标"未响应" → 嫌疑 ③，用任务管理器右键 grokfree.exe 生成转储，看主线程栈是否停在锁等待；
2. **加耗时日志**：在 `spawn_agent` 里对 probe / spawn / initialize / session_load 各打一条带耗时的 `tracing::info!`，日志在 `%LOCALAPPDATA%\GrokFree\logs`。卡死后看最后一条停在哪一步；
3. **看进程**：卡住时任务管理器里若有僵死的 `grok.exe`（或多个），对应嫌疑 ② 的 CLI 挂起。

### 2.4 P0 修复清单（最小改动，不重构）

| # | 改动 | 位置 | 说明 |
|---|------|------|------|
| 1 | **拆掉全局 busy**：发送一轮对话不再置全局 `busy`（会话状态本来就有每会话的 `running`，UI 用它即可）；`busy` 只保留给"正在创建/恢复"且**只锁当前这一个会话的入口**，不再阻止切项目和恢复其他会话 | `useComposerActions.ts`、`useResumeSession.ts`、`App.tsx` 里 `busy` 的消费点 | 对应 grok-app 的原则：「切换会话永不阻塞在忙轮次上」 |
| 2 | **给恢复链路加短超时**：probe 5s、initialize 30s、session/new 30s、session/load 120s（`request()` 加一个可选超时参数即可）。参考值：grok-app 的预算是**连接全程 90s、握手 60s、杀进程 5s**（`session_manager/types.rs`） | `acp/client.rs`、`config.rs` | 失败快、报错真，好过 600s 白等 |
| 3 | **probe 结果缓存**：`grok --version` 结果缓存（如 5 分钟 TTL，设置改动或 spawn 失败时失效），不要每次 spawn 都探测 | `supervisor/mod.rs` `spawn_agent`、`config.rs` | 顺带让新建会话明显变快 |
| 4 | **恢复可取消**：恢复期间给界面留一个「取消」入口，实现就是 `client.kill()`（`fail_all_pending` 已能立刻打断所有在途请求） | 前端恢复态 UI + 一个新 command | 保底逃生门 |
| 5 | **同步 command 全部改 async（或 `#[tauri::command(async)]`），且不再持 `desktop` 锁跨 `save()` 写盘**：clone 出数据、锁外写文件 | `commands/mod.rs`、`commands/disk.rs`、`config.rs` `DesktopState::save` | 消灭嫌疑 ③ 的窗口级冻结 |

验收标准：任一会话流式输出期间，切项目、点开/恢复其他会话 100ms 内有响应；CLI 假死时恢复在 30–120s 内报错而非无限等待；不再出现整窗"未响应"。

## 3. 值得借鉴 grok-app 的机制（按价值排序）

以下全部给出 grok-app 内的落点文件，抄思路为主；**若直接搬代码块，遵守 §5 的 MIT 要求**。

1. **进程/轮次治理策略**（`src-tauri/src/session_manager/mod.rs` 头注释、`process.rs`、`process_limits.rs`）：
   - 切换会话永不取消忙轮次，忙会话降级为 background 继续接收事件——GrokFree 的 Supervisor 已经是每会话独立进程，缺的只是**别让 UI 层把它们串起来**（P0 修复 #1 即此事）；
   - 进程数上限（默认 8）+ 闲置回收（30 分钟）：GrokFree 目前只有手动"休眠"，跑多了内存失控。加一个「闲置 N 分钟自动休眠」定时器即可，meta 保留、随时可恢复。
2. **流静默看门狗 + 长工具心跳**（`stream_stall.rs`、`tool_heartbeat.rs`）：流式静默超过阈值先做"无声自愈"（RPC 其实已结束、孤儿工具收尾），再弹「继续等待 / 结束本轮」——**从不自动取消用户发起的轮次**。GrokFree 目前 600s 超时后直接报错，介于"傻等"和"武断"之间，这套策略明显更好。
3. **权限分级 + 持久化**（`permission.rs`、`permission_rules.rs`）：AllowOnce / AllowForSession（会话级允许缓存）/ 写回 CLI `config.toml [permission]` 的 allow/deny/ask 规则（deny > ask > allow）。GrokFree 只有全局 ask/always-approve，最实用的一档"**本会话内允许此类工具**"正好缺失，且规则写在 CLI 配置里 CLI 终端里也生效。
4. **崩溃遗留轮次修复（turn lease）**（`turn_lease.rs`、`turn_interrupt.rs`）：开轮时写一个磁盘租约，宿主进程崩溃后下次启动能把该会话标成"已中断"而不是看起来正常结束。GrokFree 崩溃后会话状态全靠猜，属低成本高收益。
5. **宿主侧纯状态机**（`session_fsm.rs`）：Idle/Connecting/Ready/Streaming/AwaitingPermission/Disconnected 的迁移集中在 Rust、前端只投影快照。GrokFree 的字符串 status + `client_gen` 防陈旧事件已是雏形，把迁移规则收拢成纯函数可以消掉一类"状态残留"bug。
6. **自有会话日志 + 写盘节流**（`store.rs`、`journal_throttle.rs`）：grok-app 不依赖回放 CLI 的 `chat_history.jsonl`，自己按会话存 messages 且中流写盘 ≥500ms 节流。GrokFree 的磁盘回放（`sessions_disk.rs` 1100 行的容错解析）是脆弱面——CLI 换格式就全崩。**中期**值得换成：实时事件自己记日志，CLI 历史仅作导入源。
7. **切会话的前端手法**（`src/hooks/useSessionNavigation.ts`）：切换时先自增"代数 token"作废旧的异步写入 → 先绑定视图并**用缓存立即上屏** → 从本地日志水合 → ~500ms 后再与 CLI 历史做延迟对账 → 连接进程也做 ~350ms 防抖。GrokFree 的 `client_gen` 已有同思想的雏形，前端切换可以照这个套路把"先响应、后补全"做彻底。
8. **忙时消息排队**（`useSendQueue.ts` / `sendQueue.ts`）：轮次进行中用户继续输入，消息进队列、轮次结束自动发出，而不是禁用输入框。配合 P0 拆 busy 后体验提升明显。
9. **UI 零件（可选）**：消息/会话列表虚拟化；从任意助手回复 fork 新会话；`/attach-chat` 把旧会话作为上下文引用（`session_attach.rs`，有压缩预算设计）；Git worktree 识别与单会话切换（`cli_worktrees.rs`）。这些是锦上添花，放阶段 2。

> 另外确认：grok-app **没有**用 Windows Job Object，只靠 `CREATE_NO_WINDOW` + `kill_on_drop`；GrokFree 的 Job Object 兜底（`job_object.rs`）反而是自己的长处，保留。

## 4. 不建议照搬的部分

| 模块 | grok-app 落点 | 不搬理由 |
|------|--------------|---------|
| 全渠道 IM 桥接（飞书/TG/Discord/企微/微信/QQ…11 家） | `remote_im/` | 整个子系统 + 各平台协议维护；个人桌面自用无此需求 |
| 手机 Web 镜像 / LAN 隧道 / REST API | `mirror/`、`serve.rs` | 引入网络面与鉴权负担，与"本机工作台"定位冲突 |
| 桌宠 / 皮肤 / 壁纸 / 语音 | `pet_window.rs`、`skin_*.rs`、`voice_*.rs`、`wallpaper_source.rs` | 纯个性化包袱，约几十个模块 |
| 图像/视频生成（Imagine）、媒体服务器 | `media_*.rs`、`image_thumb.rs`、`video_poster.rs` | 依赖官方账号能力，超出 CLI 客户端范围 |
| 多账号/额度热力图/中转 provider 管理 | `account*.rs`、`providers.rs`、`supergrok_quota.rs` | GrokFree 单账号共享 `~/.grok`，够用 |
| 15 语言 i18n、代码库索引/记忆嵌入、自动化编排 | `i18n/`、`agent_codebase_indexing.rs`、`agent_memory*.rs`、`automation_runner.rs`、`agent_workflows.rs` | 维护面远超单人项目承受力 |
| 内置 CodeMirror 编辑器 / 富媒体预览 | 前端大块 | GrokFree 的"外部编辑器/终端"原则（DESIGN D10）更省事，除非日后真的天天要在应用里改文件 |

一句话：**grok-app 是"平台"，GrokFree 是"工具"。抄它的骨骼（治理策略），别抄它的体重。**

## 6. 分阶段计划（单人 Windows 体量）

### 阶段 0 —— 解卡（P0，先做）

即 §2.4 的 5 条。涉及文件集中：前端 `useComposerActions.ts` / `useResumeSession.ts` / `App.tsx`，Rust `acp/client.rs` / `supervisor/mod.rs` / `commands/*.rs` / `config.rs`。改动是"拆标志、加超时、加缓存、锁外写盘"，无结构性重构。做完先在真机验证 §2.3 的现象消失。

### 阶段 1 —— 高价值借鉴

1. 闲置自动休眠 + 并发进程上限（参考 `process_limits.rs` 的默认值与钳制逻辑）；
2. 流静默看门狗：静默 N 秒弹「继续等待 / 结束本轮」，配合"无声自愈"（先检查 RPC 是否其实已完成）；长工具期间发心跳避免误报；
3. 权限升级：弹窗加「本会话内允许」（会话级允许缓存）；设置页可读写 CLI `config.toml [permission]` 规则；
4. 忙时消息排队（§3-8）：轮次进行中允许继续输入并排队发送。

### 阶段 2 —— 可选增强（想做再做）

1. turn lease + 启动时中断修复；
2. 自有会话日志（节流写盘），CLI 历史降级为导入源；
3. 状态机收拢为纯函数 + 单测；
4. fork 会话 / attach 旧会话为上下文 / worktree 切换 / 列表虚拟化。

## 7. 不确定性声明

- 本文在 Linux 环境通读代码得出，**未在 Windows 真机复现卡死**。§2.2 的嫌疑 ①② 有直接代码证据（拒绝分支、无超时调用链），置信度高；嫌疑 ③ 是机制上成立但未观测，先按 §2.3 分辨冻结类型再决定投入。
- grok-app 演进很快（对照的是 2026-08-25 的 `fcfa63d`），文中文件路径以该提交为准。
- `session/load` 的耗时上限取决于 Grok CLI 行为，本文给的 120s 建议值需要真机按实际大会话校准。
